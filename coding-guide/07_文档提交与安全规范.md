## 二、文档规范（文档头 / 版本 / 存档）

所有 `document/` 与根级元文档（readme/code-router/memory）必须：

### 文档头部（必备字段）

```
> **文档创建时间**：2026-10-12 10:00:00
> **最后修改时间**：2026-10-12 10:00:00
> **当前版本**：V_1.0          （形式 V_1.0 / V1.0 均可，保持与同类文档一致）
> **适用对象**：谁该读本文
> **核心目标**：一段话说清本文要解决什么
> **文档简略描述**：一至两句概述内容
```

### 文档大纲

- 文档开头应有"文档大纲"（章节列表），方便读者定位（用户规则要求文档具有引导性）。

### 末尾

- **版本变化记录**：列出 V1.0 起每个版本的变更，说明"本版本较上一版本的变化"。

### 版本存档

- 主要变更后，给文件名加版本号存档：`文档名_v[1.0].md`，旧版本保留（如 `林工_基础平台_功能包开发指南_v1.2.md` 与其 v1.0/v1.1 存档）。

## 三、文件分类存放

| 内容 | 存放目录 | 说明 |
| --- | --- | --- |
| 方案 / 需求讨论 | `document/` | 带版本号 |
| 代码 | `code/` | 见 01 指引目录归属 |
| 部署文件 | `code/dist/` | **只读，禁止修改**（部署程序生成） |
| 临时文件 | `temp/` | 含验证脚本、截图 |
| 日志 | `log/` | 执行代码产生的日志 |
| 产物 | `output/` | 执行代码产生的文件 |
| 其他既有目录 | 保持原结构 | 不乱动 |

> 本次 `coding-guide/` 为 AI 开发操作手册（元文档），放置于仓库根目录，与 `readme.md`/`code-router.md`/`memory.md` 并列。

## 四、Git 提交约束

- **明确的提交信息**：一句话说明"为什么"，避免默认信息（如 "update"、"fix"）。
- **明确的提交范围**：只提交本次相关文件，避免多余文件（尤其 .env、截图、临时产物）。
- 提交前检查：
  - `git status` 看变更；
  - `git diff` 复核；
  - 按仓库既有提交风格组织 message。
- **只在用户明确要求时提交**；不擅自 push。
- 不执行破坏性 git 命令（`reset --hard`、`clean -f`、force push 等），除非用户明确要求并确认。

## 五、安全红线

以下内容**必须严格遵守**：

1. **个人密码、令牌、账号凭证、API Key、Access Token、Refresh Token、Cookie、私钥与私密配置不得进入源码**。
2. **密钥一律走环境变量或安全配置**（`.env`、`config/*` 读 Env），禁止写死。
3. `.env` 等配置文件**必须进忽略规则**，避免推到远程仓库（当前 `.env` 在 `code/host/.env`，已在忽略范围，勿改其忽略状态）。
4. 涉及 UAIS 等外部凭证的测试，用 Fake/桩实现或隔离临时目录，不联网、不写死真实令牌。
5. **不执行破坏性命令**（`git reset --hard`、批量删除、清空目录），除非用户明确要求并确认目标路径。
6. 审计敏感操作：高危管理动作必须 `auditTrail()->log(...)` 留痕（见 02 指引 §六）。

## 六、经验沉淀（memory.md 维护）

`memory.md` 是智能体的长期记忆，按分类持续维护：

| 分类 | 记录什么 |
| --- | --- |
| `[vault]` | 项目当前状态、关键结论、遗留待办 |
| `[skill]` | 重复出现且验证有效的流程/方法 |
| `[eval]` | 失败案例（问题→根因→教训） |
| `[rule]` | 重复出现的规则要求（源自 agents.md / 用户偏好） |
| `[hooks]` | 自动化校验逻辑、门禁清单 |

- 踩坑/验证通过后，及时把结论写回对应分类，并更新 `memory.md` 头部"最后修改时间"与版本变化记录。
- `code-router.md`：新需求/实现落地后回填"需求编号 → 代码点位"映射。
